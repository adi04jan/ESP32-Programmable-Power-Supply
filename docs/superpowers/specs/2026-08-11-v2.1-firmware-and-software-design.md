# Voltbench v2.1 — Firmware & Software Design

**Date:** 2026-08-11 · **Branch:** `v2-hardware` · **Status:** design approved, not yet implemented
**Hardware:** `Hardware/HARDWARE-DESIGN-V2.md` (commits 6ee5313 → 36db63f)

This is the single source of truth for the v2.1 software across all four surfaces:
device firmware, web UI, OLED/button panel, and the standalone PC application.
Where the three parallel design tracks disagreed, §2 records the resolution and why.

---

## 1. Scope and locked decisions

v1 is a 3-output supply where only channel 1 has variable voltage and **there is no
current sensing or control of any kind**. v2.1 is a 2-channel supply where each
channel has hardware CC *and* CV. Almost nothing in the control path survives.

| Decision | Choice | Rationale |
|---|---|---|
| MCU | ESP32-C3 Super Mini | fits with 1 pin spare; keeps the whole WiFi/OTA/web stack |
| Channels | 2 × (1.0–20 V, 0–2.048 A) | hardware CV + hardware CC per channel |
| Setpoints | MCP4728 quad DAC | A=CV1 B=CC1 C=CV2 D=CC2, internal 2.048 V ref |
| Sensing | INA219 ×2 | high-side shunt; ESP32 ADC cannot do this (§9) |
| Temperature | MCP9700 analog on GPIO4 | OTP only needs ±2 °C |
| Local UI | SSD1306 + 3 buttons | both channels visible, cursor-based |
| PC software | Python: library + CLI + PySide6 GUI | sync API, one daemon thread hidden in transport |
| Transport | WiFi primary, USB serial fallback | serial is the *recovery* path — must not need the heap |
| Features | protection, CC-mode toggle, logging, sequencing, presets, power-on state | all confirmed in scope |

**The inverted CV mapping governs every failure mode.** `Vout = 20.18 − 9.52·Vdac`,
so **DAC code 0 = 20.18 V**. Any path that leaves the DAC unwritten is a 20 V path.
Most of the firmware's CV work is *proving it wrote what it thinks it wrote* before EN
goes high.

## 2. Conflict resolutions

The three tracks were designed independently. Four genuine conflicts:

### 2.1 UI task placement → **inside the control task, no mutex**

The firmware track wanted a separate `ui` task at priority 2 behind an I²C mutex,
because a full 1024-byte SSD1306 frame is ~24.5 ms and would blow a 20 ms control
tick. The OLED track wanted `ui_tick()` called from the control task so state reads
need no synchronisation at all.

**Resolved in favour of the control task**, because the OLED track's own 6 ms
per-tick flush budget already answers the firmware track's objection — provided
full repaints are chunked to that same budget rather than allowed one 24.5 ms
blast. A screen transition then paints over ~5 ticks (100 ms), which is
imperceptible in practice.

This is strictly simpler than either proposal: **one fewer task, and no I²C mutex
anywhere in the firmware**, because the control task becomes the sole owner of the
bus (DAC, both INA219s, and the display). It also preserves "one owner per resource"
from `CLAUDE.md` without introducing a new primitive.

### 2.2 Serial protocol → **SCPI-flavoured commands, sigil-disciplined replies, JSON only where it earns it**

The PC track proposed sigil-prefixed JSON-lines; the firmware track proposed
SCPI-flavoured text. The firmware track's argument is decisive and wins the request
format: **the serial port exists for recovery, and recovery scenarios include heap
exhaustion.** A JSON parser needs ArduinoJson and therefore the heap, so it fails
exactly when it is needed. A tokeniser over a 96-byte stack buffer does not.

Three things are adopted from the PC track:

- **A `! READY …` banner on boot** so a host can detect a mid-stream reboot, flush its
  RX buffer, and fail pending requests instead of hanging.
- **Structured replies where a machine needs them** — but built with `snprintf` into a
  fixed stack buffer, never ArduinoJson. `MEAS? 1` returns positional CSV for humans;
  `STATE?` returns one line of JSON for machines. Both are heap-free.
- **Telemetry off by default**, so plugging into PuTTY gives a readable console rather
  than 4 Hz of JSON.

**Request tags are dropped.** The PC client is synchronous and issues one command at a
time, so replies cannot arrive out of order; the sigil alone distinguishes an
asynchronous event from a reply. Tags would be unused complexity on both sides.

### 2.3 Setpoint writes → **relative `adj_*`, not absolute**

The OLED track requires relative commands, and this is the right call for everyone: it
**structurally eliminates the remote-edit race** rather than arbitrating it. Three ▲
presses always mean "+3 steps from whatever the authoritative value is when the
control task drains the queue", never "write 12.03" computed from a value that went
stale in the meantime. No shadow copy, no rebase logic, no reconciliation state
machine. `apply_command` gains `OP_ADJ_V` / `OP_ADJ_I` alongside the absolute forms
(which presets and remote clients still use).

### 2.4 Status frame → one shape, settled now

Both tracks independently chose a nested `ch[]` array, so only details differed. This
is the frozen shape; the web UI, PC client, and OLED all read it:

```json
{"ts":123456,"up":940,"api":2,
 "ch":[{"en":true,"v":5.002,"i":0.312,"w":1.561,"vset":5.0,"iset":1.0,
        "mode":"cv","prot":"ok","reason":"","cc_mode":"limit",
        "ovp":21.0,"ocp":2.048}],
 "temp":41.5,"temp_src":"mcp9700",
 "seq":{"state":"running","step":3,"n":8,"el":1240},
 "log":{"on":true,"n":812,"cap":2048},
 "cal":[true,true]}
```

Decisions inside it: `w` not `p` for power (unambiguous); protection is **per-channel**
(`prot` + `reason`) rather than a single top-level block, because the two channels trip
independently; `ovp`/`ocp` ride in the frame despite costing ~30 bytes, because the
OLED uses OVP as its live setpoint ceiling and fetching it separately would be a sync
hazard; `api:2` enables version-skew detection; `temp_src` matters now that there is a
degraded fallback. The whole frame is filled from **one seqlock read**, so it is
internally consistent by construction.

## 3. Firmware architecture

### 3.1 Tasks

ESP32-C3 is **single-core** — every `xTaskCreatePinnedToCore(…, 0)` in v1 is
decorative, and priority ordering *is* the concurrency design.

| Task | Prio | Stack | Owns exclusively | Period |
|---|---|---|---|---|
| `wifi` / `tcpip` (IDF) | 23 / 18 | — | radio, lwIP | — |
| **`ctrl`** | **5** | 6144 | **all I²C** (DAC, INA×2, OLED), temp ADC, EN/CAL GPIO, protection FSM, sequencer, log ring, `ui_tick()` | 20 ms |
| **`btn`** | 4 | 2048 | 3 GPIOs, nothing else | 5 ms |
| `async_tcp` | 3 | 16384 | HTTP/WS sockets | event |
| **`con`** | 2 | 3072 | USB-CDC RX + line parser | 10 ms |
| `wifiMgr` | 2 | 8192 | WiFi lifecycle (v1, verbatim) | 60 s |
| `loopTask` | 1 | 8192 | telnet + `/logws` pumps, WS push, MQTT, captive DNS, **deferred NVS writes** | 2 ms |

**`ctrl` moves from v1's priority 2 to 5** — above AsyncTCP. An over-current trip must
not queue behind a WebSocket burst. The cost is one absolute rule: **`ctrl` must never
block without yielding**, or AsyncTCP starves and the device drops off the network. Its
duty is ~3 ms of the 20 ms tick plus up to 6 ms of display flush; the rest is
`vTaskDelayUntil`.

**`con` is a separate task, not part of `loop()`.** The serial console exists to rescue
a device whose network stack has wedged — the exact HWCDC scenario in `CLAUDE.md`. In
`loop()` it would die with the thing it exists to rescue.

### 3.2 Shared state — three mechanisms, no others

**(a) Telemetry out — seqlock.** `ctrl` publishes one `VbSnapshot` behind an even/odd
version counter. This replaces v1's loose volatiles, which can report voltage from tick
N and trip state from tick N+1 — producing "output OFF but reading 12 V" on screen. The
retry loop provably terminates here because every reader (`async_tcp` 3, `con` 2,
`loop` 1) is strictly below the writer (5), so a reader can be preempted mid-copy but
the writer can never be preempted by a reader. Safe to call from an AsyncTCP callback;
never blocks.

**(b) Setpoints in — last-writer-wins volatile cells**, 32-bit aligned scalars, atomic
on RV32. `ctrl` diffs them each tick.

**(c) Everything else — one FreeRTOS queue**, 16 deep, `xQueueSend(…, 0)` so it is
legal from an AsyncTCP callback. Carries `adj_*`, `clear_trip`, cal, log, sequencer,
and preset operations. Full → `VB_EQFULL` → HTTP 503.

**Forbidden inside AsyncTCP callbacks:** `Wire.*`, `Preferences.*` (a 10–40 ms flash
erase stalls the entire network stack), anything blocking, any `String` over 1 KB.

### 3.3 File layout — the mid-file-include trap, killed properly

v1 is one translation unit with `firmware-additions.h` included at line 457 and
depending on prior declarations. The fix is not to move the include — it is to **stop
having one translation unit.** The Arduino IDE compiles `.cpp` files in the sketch
folder as separate TUs, so textual ordering stops mattering entirely.

```
ESP32_power_supply.ino   setup() + loop() + task creation ONLY (~150 lines)
vb_config.h              pins, addresses, limits, version, #pragma GCC optimize("Os")
vb_state.h/.cpp          VbSnapshot, seqlock, command cells, queue handle
vb_cal.h        PURE     2-point fit, code<->mV, all clamping
vb_protect.h    PURE     protection + CC state machine
vb_seq.h        PURE     step schema, validator, executor tick
vb_log.h        PURE     ring append, line formatter, chunk cursor
vb_cmd.h        PURE     line tokeniser, string -> VbCommand
vb_ui_logic.h   PURE     digit/step/carry, velocity ramp, formatters, CC hysteresis
vb_hal.h/.cpp            MCP4728, INA219, MCP9700 ADC, SSD1306 init, GPIO
vb_control.h/.cpp        the ctrl task
vb_nvs.h/.cpp            Preferences wrapper, g_nvs_mux, dirty-flag flusher
vb_net.h/.cpp            ex-firmware-additions.h: routes, WS, MQTT, wifiMgr, auth
vb_console.h/.cpp        con task + telnet (shared parser)
vb_ui.h/.cpp             rendering, screens, button event consumption
```

Three Arduino-IDE gotchas that must be written into the header comments:

- `.cpp` files in a sketch folder **do not** get an implicit `#include <Arduino.h>`.
- Files in subdirectories **are not compiled** unless the directory is named `src/`.
  Keep it flat — flat files also get IDE tabs.
- `#pragma GCC optimize("Os")` is **per-TU**. It lives in `vb_config.h`, which every TU
  includes first. Losing it costs ~60 KB of flash.

`PURE` headers include only `<stdint.h>`, `<string.h>`, `<math.h>` — no `Arduino.h`, no
`String`, no FreeRTOS. That constraint is what makes the host tests possible; enforce it
by compiling them with `-Werror` in `tools/host_test`.

### 3.4 Control path

Per-channel calibration, 24 bytes, stored as `v0`/`slope` rather than gain-and-offset
because both are physically meaningful, directly invertible, and **independently
bounds-checkable** — which is what stops a corrupt fit from commanding 20 V:

```c
struct ChanCal { float cv_v0_mV, cv_slope_uV, cc_gain, cc_off_mA,
                       ina_v_gain, ina_i_gain; };

cv_code(mV) = round((cal.cv_v0_mV - mV) / (cal.cv_slope_uV / 1000))
cc_code(mA) = round((mA + cal.cc_off_mA) * cal.cc_gain)
```

Two-point fit at **code 3800 (~2.1 V)** and **code 1700 (~12.1 V)** — a wide baseline,
and the low point sits inside the self-cal load's ≤3 V interlock so one routine trims
both. Accept only if `v0 ∈ [18500, 22000] mV`, `slope ∈ [4300, 5300] µV/code`, and the
codes are ≥1500 apart; otherwise keep nominal and flag `cal_valid = false`.

Clamp order, all host-tested: absolute limits → user soft ceiling → code conversion →
code clamp to `[cv_code(vmax), 4069]` (4070–4095 are below-spec) → **assert-back**:
`cv_mV(code) ≤ mV + 250`, and on violation refuse the write and latch `HW_FAULT`.

**Boot sequence — steps 6 and 10 are the ones people skip, and they are the difference
between "the DAC was probably written" and "the DAC was written":**

1. `pinMode` + `LOW` on EN1/EN2/CAL1/CAL2 — **the first statements in `setup()`**
2. Serial, `setTxTimeoutMs(0)`, banner
3. `Wire.begin(6, 7, 400000)`; probe 0x3C, 0x40, 0x41, 0x60 — **0x60 missing ⇒ outputs
   can never be enabled this boot**
4. MCP4728 single-channel writes: A=4095, C=4095 (minimum volts), B=0, D=0
5. INA219 ×2: 32 V range, PGA/8, 12-bit 8-sample averaging, cal register `0x1000`
6. **Read back all four DAC registers.** Any mismatch ⇒ `HW_FAULT`, refuse to enable.
   Also read DAC EEPROM and warn loudly if CV≠4095 or CC≠0
7. Load NVS: cal, presets, protection limits, power-on policy
8. Compute codes; write **CC first, then CV** (so the limit is never transiently high)
9. `vTaskDelay(5 ms)`
10. **Read back all four DAC registers again.** Mismatch ⇒ abort, no enable
11. Apply power-on policy; stagger CH2 by 100 ms to avoid a double inrush
12. `STARTING` state — 250 ms protection grace window

Setpoint changes while enabled write CC then CV with no settle wait and no verification
loop. If the new voltage is lower the output decays at the load's RC; that is why OVP is
**absolute, not tracking** — a step-down must not self-trip.

### 3.5 Protection + CC state machine

```
                 en_cmd && !hw_fault              250 ms
      OFF ──────────────────────────► STARTING ──────────► CV ◄──────┐
       ▲                                                    │        │ !cc 200 ms
       │ en_cmd=0                                  cc 60 ms │        │
       │                                                    ▼        │
       │                                                   CC ───────┘
       │                                                    │
       │         ovp | ocp | otp | cc_trip | hw | interlock │
       │   ┌────────────────────────────────────────────────┘
       │   ▼
       │  TRIPPED(reason)   EN low  AND  DAC forced to CV=4095 / CC=0
       │   │  clear_trip AND fault absent
       │   ▼
       └─ CLEARING (200 ms, rewrite DACs) ──► OFF
```

| Check | Threshold | Debounce | Why |
|---|---|---|---|
| OVP | absolute, default 21 000 mV, hard cap 21 500 | 20 ms | absolute — a step-down legitimately sits high for seconds into a capacitive load |
| OCP | `min(ocp, i_limit + 150 mA)` | **100 ms** | must clear both the analog CC band (±75 mA) *and* the integrator-windup overshoot. OCP detects "the analog loop failed" — it is not the limiter |
| CC enter | `i ≥ limit − max(50 mA, 5%)` **and** `v < vset − 250 mV` | 60 ms | >3× the integrator's 10 ms τ; 250 mV clears ripple + regulation error |
| CC exit | predicate false | 200 ms | asymmetric and sticky-on, so the badge cannot flicker |
| CC_TRIP | in CC and `cc_mode == trip` | 60 ms after CC entry | ≈120 ms total from onset |
| OTP | > 80 °C | 1 s | thermal is slow; **trips both channels** |
| HW_FAULT | I²C NACK or DAC readback mismatch | 3 ticks | trips both channels |
| Regulation warn | `|v − vset| > 1 V`, enabled, not CC | 3 s | **log only** — catches a blown FB resistor without nuisance trips |

**A trip drives the DAC to safe as well as dropping EN**, so a stuck EN net cannot hold
20 V. **Clearing never auto-re-enables** — a latch that re-arms itself is not a latch.
Clear is refused while the fault persists (OVP with `v` still high, OTP within 5 °C
hysteresis, `hw_fault` set); OCP and CC_TRIP have no persistent condition so they clear
immediately. Latches are RAM-only: a power cycle clears them, deliberately, so a
headless unit cannot strand itself.

**CC-mode toggle, as confirmed:** `limit` and `trip` differ by **exactly one edge**
(`CC → TRIPPED`). In *both* modes the analog CC DAC stays programmed at the user's
limit — it is what bounds fault current during the ~120 ms before firmware latches.
Raising it in trip mode so the reported trip current looks "cleaner" would trade a real
backstop for cosmetics. Do not.

### 3.6 NVS

Keep namespace `voltbench` and `g_nvs_mux`; migrate additively via a `schema` key
(schema < 2 ⇒ erase `calmap`/`calok`, write `schema=2`). **Do not factory-reset** — that
destroys WiFi credentials and forces a captive-portal dance on every dev flash.

The partition is **20 KB**, which is the binding constraint: sequences live in RAM, not
NVS. New keys: `cal1`/`cal2` (24-byte blobs, one key each — not six), `calok*`,
`calsrc*`, `pomode*`/`pov*`/`poi*`, `lastv*`/`lasti*`/`lasten*`, `ovp*`/`ocp*`/`otpc`,
`ccmode*`, `vmax*`/`imax*`, `presets` (176-byte blob, 8 × 22 B), `loghz10`, `logauto`.

**Wear footgun:** writing `last_*` on every setpoint change would burn the partition
during a sequencer ramp (50 writes/s). Rule: at most **once per 30 s, only if changed,
never while a sequence runs**. And NVS writes happen only on `loopTask` (priority 1,
harmless to block) via dirty flags — never on `ctrl` or `async_tcp`.

### 3.7 Logging

```c
struct LogRec {            // exactly 12 bytes
  uint32_t t_ms;
  uint16_t v[2];           // mV
  uint16_t i[2];           // low 12 bits mA; bit12 en, bit13 cc, bit14 tripped
};
static LogRec g_ring[2048];   // 24 576 B static — not malloc
```

Power is derived at CSV time, never stored. Budget: ~34 KB of new static/stack against
~150–170 KB free heap, leaving ≥70 KB at the worst moment (mid TLS pull-OTA). Log
`ESP.getFreeHeap()` and stack high-water marks every 10 s — that number decides whether
the ring can later grow to 4096 records.

| Rate | Duration | | Rate | Duration |
|---|---|---|---|---|
| 10 Hz | 3 min 25 s | | **1 Hz (default)** | **34 min** |
| 5 Hz | 6 min 50 s | | 0.2 Hz | 2 h 50 min |
| 2 Hz | 17 min | | 0.1 Hz | 5 h 41 min |

Max 10 Hz — 50 Hz would give 41 s of buffer and alias the 20–30 mV ripple into garbage.
**On trip, force one record unconditionally** regardless of rate or run state; that
guarantees the CSV always contains the trip point, and it is far cheaper than a
pre-trigger ring.

CSV download uses `beginChunkedResponse` with a 12-byte per-request cursor, pausing the
ring for a tear-free snapshot and auto-resuming after 30 s if the client vanishes. **The
load-bearing rule: never build the CSV into a `String`** — 107 KB with doubling
reallocation is instant OOM. `snprintf` whole lines into the supplied buffer, always.

### 3.8 Sequencer

Fixed 16-byte steps, `SeqStep g_seq[64]` static, no allocation while running. Ops:
`SET`, `RAMP`, `WAIT`, `WAIT_UNTIL`, `OUTPUT`. Validation at `PUT` time returns the
failing **index** (`{"err":"step","idx":3,"why":"v out of range"}`), which is what makes
it usable.

Three safety defaults, each learned the hard way in this class of instrument:

- **End of sequence turns outputs off by default.** A sequence that ends silently
  leaving 20 V on the bench is how you kill a DUT.
- **A trip mid-sequence aborts and disables *both* channels.** In a two-rail test,
  leaving one rail up after the other dies back-feeds the DUT.
- **Never auto-resume after an unexpected reset.** Resume-after-crash on a power supply
  is how you discover your DUT's real absolute-maximum ratings. Report
  `seq_aborted_by_reset` so the UI can say what happened.

Sequences are RAM-only: they survive the browser closing (the stated requirement), not a
reboot. A LittleFS library in the unused 448 KB `spiffs` partition is a later phase and
does not change the executor.

## 4. API contract

### 4.1 `apply_command`

```c
enum VbOp { OP_SET_V, OP_SET_I, OP_ADJ_V, OP_ADJ_I, OP_ENABLE, OP_ALL_OFF,
            OP_CC_MODE, OP_CLEAR_TRIP, OP_SET_OVP, OP_SET_OCP, OP_SET_OTP,
            OP_LOG, OP_SEQ, OP_PRESET_SAVE, OP_PRESET_LOAD, OP_CAL_AUTO, OP_CAL_PT };
enum VbErr { VB_OK, VB_EBADCH, VB_ERANGE, VB_ECLAMPED, VB_EBUSY, VB_ETRIP,
             VB_EINTERLOCK, VB_EQFULL, VB_EUNKNOWN, VB_EHW };

VbErr apply_command(const VbCommand &c);                        // typed core
VbErr apply_command(const String &action, uint8_t ch, float v); // string front-end
```

Six transports still funnel through one dispatcher. HTTP/WS/MQTT/telnet/serial use the
string front-end; the OLED and the sequencer call the typed core directly, avoiding a
`String` allocation per button press. **Every setpoint change stamps `last_src` and
bumps `rev_set`** — the panel's remote-change detection is built entirely on those two
fields. The typed error enum exists so the panel can show `CLAMPED 20.00V` or
`TRIP ACTIVE` instead of silently swallowing a press.

### 4.2 REST + WebSocket

Unchanged and **not to be touched**: `/api/wifi/*`, `/api/ota/*`, `/api/mqtt/test`,
`/api/reboot`, `/api/factory_reset`, `/logws`, `POST /api/login`.

| Method | Path | Notes |
|---|---|---|
| GET | `/api/status` | new shape (§2.4), `Cache-Control: no-store` — **breaking** |
| GET | `/api/info` | adds `api:2`, `channels`, `vmin/vmax/imax`, `temp_src`, `hw:{}` |
| POST | `/api/control` | `output` → `ch`; accept both for one release |
| POST | `/api/channel/{n}` | **new** — atomic `{v?,i?,en?,cc_mode?}`; what the UI actually needs |
| GET/POST | `/api/prot` | **new** — limits + state |
| POST | `/api/prot/clear` | **new** — 409 `{err:"fault-present"}` if still faulted |
| GET/POST | `/api/log` · GET `/api/log.csv` | **new** — chunked CSV, `?since=` |
| GET/PUT | `/api/seq` · POST `/api/seq/{run,stop,pause,resume}` | **new** |
| GET/PUT/DELETE | `/api/presets[/{slot}]` · POST `/api/preset/{slot}/apply` | **new** |
| GET | `/api/cal` · POST `/api/cal/{auto,point,clear,dac_eeprom}` | replaces the sweep API |
| GET | `/api/settings` | **new** — v1 had no GET |

Deleted: `/api/cal/sweep`, `/api/cal/status` (the 128-entry map is gone), all
`output3`/`voltage3`.

**WebSocket edge pushes:** `ctrl` sets `g_push_now` on any trip, CC transition, or
sequencer step change, and `loop()` honours it once, bypassing the 250 ms rate limit —
but **still** checks `availableForWriteAll()` and drops rather than queues. Both v1
workarounds stay exactly as they are.

### 4.3 Serial line protocol

Reply discipline — the first character classifies every line, which is what makes it
machine-parseable where v1's console was not:

```
OK                       command succeeded
OK <csv|json>            query reply
ERR <code> <text>        failure; code is a stable token
! <event...>             asynchronous (trip, seq step, telemetry, READY banner)
# <text>                 DbgPrint log fan-out
> <text>                 multi-line payload continuation
```

Commands are case-insensitive, ≤96 chars, and **the channel is always explicit** — no
stateful channel selection, which is the single biggest source of automation bugs in
real SCPI gear.

```
*IDN?                    ! READY Voltbench,4.0.0,proto 1,ch 2
VOLT <ch>,<v>   VOLT? <ch>        CURR <ch>,<a>   CURR? <ch>
OUT <ch>,<0|1>  OUT? <ch>         MEAS? [<ch>]  -> OK 5.001,0.213,1.059,CV
STATE?                   -> OK {json}          (snprintf, heap-free)
CCMODE <ch>,<LIMIT|TRIP>          PROT? <ch>    PROT:CLR <ch>
PROT:OVP <ch>,<v>                 PROT:OCP <ch>,<a>     PROT:OTP <c>
LOG <START|STOP|CLEAR>   LOG:RATE <hz>   LOG?   LOG:DUMP
SEQ:LOAD    SEQ <RUN|STOP|PAUSE|RESUME>    SEQ?
PRESET:SAVE <slot>,<ch>  PRESET:LOAD <slot>,<ch>   PRESET?
CAL:AUTO <ch>   CAL:PT <ch>,<CV|CC>,<measured>     CAL? <ch>
STREAM <hz>     (0 = off, default off)   NET?   REBOOT   HELP
```

Robustness requirements on both sides: a line over 96 bytes is discarded to the next
newline with `ERR overflow` (never a truncated command); the host sends a lone `\n`
after opening a port to flush any partial line; the host **discards any line without a
leading sigil**, which makes boot-ROM chatter and mid-line truncation harmless; on
`! READY` the host clears its buffer and fails pending requests.

**Serial is unauthenticated by default** — physical access has already crossed the trust
boundary, and locking yourself out of the recovery path is worse than the threat it
prevents. `factory_reset` and password changes are simply not exposed there. Telnet
reuses the identical parser but stays password-gated because it is network-reachable.

**Host-side, non-negotiable:** open the port with `dtr=False, rts=False` *before any
write*. Asserting either **resets the ESP32-C3** and drops your outputs mid-experiment.

## 5. OLED + button panel

### 5.1 Home screen

21 columns × 8 pages at the default 6×8 font.

```
p0  |CH1  5.00V 0.482A CV |   CH1 inverted = output ON
p1  |set  5.00V 1.000A  FB|   cursor = 5 inverted chars; FB/TR = CC action
    ---------------------
p2  |CH2 12.00V 0.000A -- |
p3  |set 12.00V 0.500A  TR|
    ---------------------
p4  |CH1  5.001V   2.412W |   detail line for the cursored channel
p5  |                     |   alert slot — deliberately empty when idle
p6  |SEL:nxt ▲▼ 0.01V     |   always states the current step
p7  |192.168.1.42     ≈   |   IP + icon strip (wifi/log/seq/remote)
```

Set-V sits directly under measured-V and set-I under measured-I; that vertical
alignment is the point of the approved layout. Home shows 2 decimals because the
INA219's 4 mV LSB plus 20–30 mV of ripple makes a third decimal dance; the full
precision lives on the detail line. Page 5 is blank by design — an inverted bar
appearing in otherwise-empty space is maximally noticeable.

**Three simultaneous CC signals:** the badge inverts, a `◄` in the set row points at the
value actually in control, and a 3-second banner fires **on entry only** (a permanently
lit banner stops being read).

**A trip takes the whole screen**, states the cause and channel in double-size text, the
measured value versus the threshold, and — critically — **what the other channel is
doing**, because a trip on CH2 must not let you assume CH1 is dead. It blinks by
toggling SSD1306 command `0xA7`/`0xA6`: two bytes per toggle, zero framebuffer traffic.

### 5.2 Interaction

Buttons: `SEL` = GPIO0, `UP` = GPIO1, `DOWN` = **GPIO21** (moved off the GPIO2 strap;
needs a 1 kΩ series resistor because the ROM drives U0TXD during boot).

| Gesture | At home | In lists |
|---|---|---|
| SEL tap | next cursor field | activate item |
| SEL 0.4 s | toggle that channel's output | back to parent |
| SEL 1.5 s | open menu | jump to home |
| ▲ / ▼ tap | ∓ one step | move selection |
| ▲ / ▼ hold | velocity ramp | repeat |
| ▲+▼ tap | cycle step size | back to parent |
| **▲+▼ hold 1.5 s** | **ALL OFF** | **ALL OFF** |

`ALL OFF` is bound in 19 of 20 states (the exception is OTA, where outputs are already
forced off). Every list has `< Back` as item 0, so escape never requires a remembered
gesture.

**Double-press is deliberately unbound everywhere.** Binding it would tax *every* press
with a 250 ms disambiguation wait — unacceptable on the button that navigates and the
buttons that change a live output voltage. The detector ships behind
`UI_ENABLE_DOUBLE = 0`; the fourth gesture the design needs is the chord, which is free.

### 5.3 Editing model

**Digit cursor with a sticky, decaying step, plus a velocity ramp.** Step cycles
coarser and wraps (0.01 → 0.10 → 1.00 → 0.01), defaults to the *finest*, and **decays
back to finest after 15 s of inactivity on that field** — so you can never walk up to
the panel, press ▲, and get +1.00 V.

| Hold elapsed | Voltage velocity |
|---|---|
| < 400 ms | one step |
| 400 ms – 1.2 s | 0.4 V/s |
| 1.2 – 2.5 s | 1.5 V/s |
| ≥ 2.5 s | 5.0 V/s |

Benchmarks: **3.30 V → 12.00 V takes 8 actions / ~4 s**; **nudging by 10 mV takes 1
press** (3 if the cursor must move first). Full range traverse is ~5.6 s of hold.

**Live-apply, coalesced at 100 ms** — the DAC sees ≤10 writes/s even during a
full-speed ramp. There is no edit mode and therefore nothing to abort: every press
moves the setpoint by a bounded visible amount and the inverse press undoes it exactly.
The three real escapes are ALL OFF, the OVP ceiling, and explicit cancel on the modal
editors used for *settings* (where you cannot see the effect and step back from it).

**OVP doubles as the setpoint ceiling.** Set OVP to 3.6 V before probing an ESP32 board
and no coarse-digit fumble can smoke it. One concept, two jobs, and it removes any need
for confirmation dialogs on setpoint edits.

### 5.4 Rendering budget

The gate that does the real work is **format-then-compare**: each dynamic field renders
into a small `char[]` and is redrawn only if the string changed. A stable rail therefore
produces *zero* display traffic no matter how much the ADC dithers below the displayed
resolution.

| Scenario | Bus share at 400 kHz |
|---|---|
| Naive full frame @ 30 fps | 74 % — infeasible |
| This design, idle | **0.6 %** |
| This design, active ramp | **2.7 %** |

Dirty tracking is one min/max column pair per page (8 entries, static). **A hard 6 ms
flush budget per tick**, priority-ordered (banner/trip → badge → measurements → detail →
hint → status) with carry-over to the next tick, bounds control-loop jitter
deterministically — and per §2.1 full repaints are chunked to the same budget rather
than blasted in one 24.5 ms write.

Burn-in mitigation is free: contrast to 1 after 10 min idle (2 bytes) and a ±1 px origin
shift every 60 s (2 bytes). **Never blank the display** — a bench supply must always
show its state.

### 5.5 Failure modes

| Failure | Display | Safety action |
|---|---|---|
| OLED dead | LED blinks 3-short-1-long | Device stays fully controllable remotely. Locally **only ALL OFF stays bound** — a user who cannot see what they are changing must not be able to change it. Re-init retried every 5 s |
| INA219 dead | `--.--V --.---A`, `??` badge (dashes never mean zero) | After 3 failures that channel's EN drops and a `SENSE` trip latches — OVP and OCP both depend on it |
| I²C bus hung | full-screen fault | 9-clock recovery ×3, then **both EN pins driven low**. EN is a plain GPIO with a pull-down, so killing outputs never depends on the bus |
| OTA | modal, 2 Hz single-page refresh | outputs forced off at start; 5 min watchdog |
| Stuck button (>30 s) | banner naming the button | latched out so auto-repeat cannot run a setpoint away |
| Brownout / crash | boot splash shows `RST BROWNOUT` | outputs off by hardware: EN pull-downs plus DAC EEPROM restoring CV=4095 |

**The invariant behind all of it:** output enable is a GPIO with a hardware pull-down,
and every failure path ends with that GPIO low. No failure mode needs a working bus,
display, or sensor to make the instrument safe.

## 6. PC software

```
voltbench/
  model.py          dataclasses + parse_status() — THE contract, no I/O
  transport.py      Transport ABC, Frame, connect_to(), reconnect supervisor
  net_transport.py  requests + websocket-client; token rotation lives ONLY here
  serial_transport.py  pyserial + the §4.3 codec
  discovery.py      mDNS resolve/browse; serial VID/PID + handshake
  device.py         PowerSupply / Channel, waits, safing, event fan-out
  csvlog.py  sequence.py  sim.py  cli.py
  gui/  app.py worker.py main_window.py channel_card.py scope.py sequencer.py style.py
```

**Sync, not async.** Bench scripts are inherently sequential (`set → wait → measure →
assert`); `await` on every line buys nothing and would drag in `qasync` and
`pyserial-asyncio`. Push telemetry needs concurrency — that is one daemon thread inside
the transport, invisible to the caller.

**The simulator is the whole strategy.** `sim.py` implements `Transport` directly, so
`connect("sim://")` returns a working `PowerSupply` with no sockets and no hardware. It
models DAC quantisation, a configurable load driving real CV/CC crossover, latched
trips, and fault injection, all on an injectable clock so a `timeout="4h"` test runs in
microseconds. **This is what lets the entire PC package be built and tested before the
firmware exists.**

```python
with connect("voltbench.local", password="admin") as psu:   # or "COM7", or "sim://"
    ch = psu.ch[1]
    ch.set(volts=5.00, amps=0.500); ch.on()
    ch.wait_until("i < 0.05", hold="30s", timeout="4h")
# outputs safed here, exception or not
```

A latched trip **raises `Trip` out of any blocking primitive**, because a wait that
silently never satisfies is the worst possible bench behaviour. The context manager
retries `all_off` across a reconnect and then *verifies* it; `Ctrl+C` runs the same
path, since that is how most bench scripts actually end. Honest limitation, documented:
no PC-side construct survives a PC crash — which is why the firmware should grow an
optional `wdt <secs>` host dead-man timer.

**CLI** uses argparse (stdlib, ~120 lines) with two additions that matter for pipelines:
`--json` on everything (exactly one object on stdout, diagnostics to stderr) and stable
exit codes — `3` no device, `4` rejected, **`5` protection trip**, `6` timeout, `7` link
lost. `voltbench seq run charge.toml; if ($LASTEXITCODE -eq 5) {…}` is the point.

**GUI** is instrument-panel, not web-app: near-black ground, CH1 amber / CH2 cyan as the
only chromatic elements, semantic colour reserved (green CV outline, filled amber CC,
red for trips *only*), and measurements in tabular-figures monospace so digits do not
jitter. Threading is absolute — the Qt main thread may import nothing but `PySide6`,
`pyqtgraph`, and `voltbench.model`; `worker.py` is the sole protocol touchpoint, and a
ten-line AST test fails the build if any other GUI file imports a transport module.
Plotting uses pyqtgraph with preallocated numpy rings (~3.5 MB for 12 h at 4 Hz), four
curve objects created once, `autoDownsample` with peak preservation, antialiasing off,
and repaint decoupled from arrival rate by a 10 Hz timer.

**Sequencer files are TOML** with a **flat step array and explicit `loop`/`end`
markers** — structurally identical to the device's fixed step array, so push/pull is a
field rename rather than a lossy flatten/re-nest. The format expresses exactly the
device's capability set; no PC-only operations.

**CSV logging** is a subscriber, not a poller, so it never perturbs the device. Merging
the device's on-device log into PC-side gaps uses a **linear timebase fit**, not a
constant offset: the ESP32 crystal drifts ~70 ms/hour, so an 8-hour run's device rows
would otherwise land over half a second out of place. Fit coefficients and residuals go
in a sidecar JSON so the correction is auditable.

Install via `pipx install "voltbench[gui]"`. Use `[project.gui-scripts]` so
double-clicking the GUI does not leave a console window behind. No frozen executable
for now — the audience is one developer who already has Python and will edit this
weekly; `pipx install --editable` is strictly better for that.

## 7. Web UI revamp

**A refactor, not a rewrite.** The file is already config-driven at the seam that
matters: a `channels[]` array, `data-*` behavioural hooks separated from styling
classes, and a single `onStatus()` funnel every update flows through. Roughly 90 % of
the CSS and all the expensive infrastructure — auth, the WebSocket watchdog with
polling fallback, OTA, WiFi management, settings persistence — is channel-agnostic and
survives untouched. **Do not touch the WS watchdog** (`Power Supply.html:958-989`); it
is battle-tested against the firmware's deliberate frame-dropping.

Budget ~450 JS lines changed across five functions — `renderChannels`,
`paintChannels`, `syncChannelControls`, `pushHist`, `drawGraph` — plus the demo backend
and some static copy.

- **New component:** the CC/CV channel card — dual readout (V and I), two setpoint
  pairs, a mode pill (reuse the existing `.badge` with its `.ok`/`.warn` variants), and
  a `.channel.cc` amber variant beside the existing `.channel.on`.
- **History graph:** the single shared Y axis at line 1397 cannot show 0–20 V, 0–2 A and
  0–60 W together. Add a V/I/P metric selector (copy the existing `.seg` wiring) or
  stacked panes against a shared time axis — the latter is better for CC/CV work, where
  you want to watch the voltage collapse and the current clamp simultaneously.
- **Bump the localStorage key to `ps_hist_v2`.** The current loader reads the old array
  with no version field, so v1 records would render as garbage. Also halve `HIST_MAX` or
  decimate; the record grows from 8 fields to ~12.
- **Delete:** the rotary dial (~90 lines that do not survive contact with four
  setpoints), the `fixed`-channel template branch, the VAR/5V/3V3 labels.
- **Note:** the page loads Inter and JetBrains Mono from Google Fonts, which **fails on
  the device** and silently falls back to system fonts. Either inline them as data URIs
  or pick system stacks deliberately.

## 8. Build order

Each phase is independently testable on real hardware and leaves a working device.
Firmware phases are sequential; PC and web work run in parallel against the simulator.

| Phase | Content | Gate |
|---|---|---|
| **0** | Multi-TU file split, no hardware change | Builds, boots, serves v1 UI. **Record baseline free heap** — it gates the log ring size |
| **1** | One channel: DAC + readback verify, INA219, EN, `ctrl` task, minimal serial. *No web, no protection, no OLED, no CC* | DAC writes with EN low produce zero output; 1→20 V sweep logged against a DMM (this table is also the Phase-2 cal data); reset mid-output drops the rail |
| **2** | Calibration: 2-point fit, bounds rejection, NVS, `/api/cal/*` | ≤±50 mV at 5 points; survives power cycle; out-of-bounds fit rejected |
| **3** | Channel 2 + CC detection | 10 Ω load, 10 V/0.5 A → reports CC, folds to ~5 V; **changing ch1 does not glitch ch2** |
| **4** | Protection FSM (host tests green *first*) | OCP latches; `cc_mode=trip` cuts a short in <200 ms; clear-while-shorted refused; grace window suppresses inrush |
| **5** | New API + web UI revamp | power-on policy correct with the 100 ms stagger; remote setpoint lands within one WS frame |
| **6** | OLED + buttons | **`ctrl` tick jitter p99 < 40 ms with the display rendering** — log it; remote change appears on the panel; local edit during a remote change resolves cleanly |
| **7** | Logging + chunked CSV | 1 Hz for 40 min wraps correctly; download during logging does not tear; heap returns to baseline |
| **8** | Sequencer | 6-step sequence completes **with the browser closed**; mid-sequence trip kills both channels; reboot does *not* resume |
| **9** | **Self-cal load — deliberately last** | interlock refuses above 3 V *measured*; 2 s deadline fires; a forced `ctrl` hang trips the task watchdog and drops CAL within 5 s |
| **10** | MQTT, OTA, telnet, the checked-in `web_page.h` build script, `AUTOMATION.md` v2 | |

PC track: `model.py` + `sim.py` first, then transport, device, CLI, GUI — all against
`sim://`, no hardware required, startable immediately.
